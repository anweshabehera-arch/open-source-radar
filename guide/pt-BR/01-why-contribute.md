# 1. Por que contribuir e o que conta como contribuição

## O que você ganha

- **Experiência no mundo real.** Você trabalha em bases de código usadas por milhares de pessoas e recebe revisões de código de profissionais experientes. Poucos cursos ou projetos pessoais oferecem isso.
- **Um histórico público.** Pull requests mesclados ficam visíveis e podem ser compartilhados como prova do que você sabe fazer. Recrutadores os consultam.
- **Habilidades melhores, mais rapidamente.** Ler o código de outras pessoas, seguir as convenções do projeto e receber comentários linha por linha ensina mais do que escrever código sozinho.
- **Pessoas.** Mantenedores e colaboradores frequentes tornam-se colegas, mentores e referências.
- **Corrigir coisas que você usa.** O bug que incomoda você provavelmente também incomoda outra pessoa.

## Como é uma contribuição na prática

A maioria das primeiras contribuições é pequena. Uma correção de bug de uma linha acompanhada de um bom teste é um ótimo primeiro pull request. Uma mensagem de erro mais clara, um exemplo ausente na documentação ou uma reprodução que transforme um relato vago de bug em algo que o mantenedor possa investigar também são boas contribuições.

## Contribuições que não envolvem código

Elas são realmente valorizadas e, muitas vezes, são mais escassas do que contribuições de código:

| Contribuição | Por que importa |
| --- | --- |
| Reproduzir relatos de bugs | Mantenedores gastam muito tempo perguntando: “você pode fornecer etapas para reproduzir o problema?”. Uma reprodução clara na issue economiza esse tempo. |
| Triagem | Identificar duplicatas, confirmar um bug na versão mais recente ou informar que algo já foi corrigido. |
| Documentação | Corrigir instruções erradas, adicionar exemplos ausentes ou explicar uma opção confusa. |
| Traduções | Muitos projetos precisam de tradutores e possuem ferramentas específicas para isso. |
| Testes | Aumentar a cobertura de comportamentos ainda não testados ou transformar um relato de bug em um teste que falha. |
| Revisões | Depois de conhecer o projeto, fazer revisões cuidadosas dos pull requests de outras pessoas é valioso. |
| Design, acessibilidade e experiência do usuário (UX) | Muitos projetos não têm designers nem pessoas para testar a acessibilidade. |
| Responder a perguntas | Ajudar outras pessoas em discussões, fóruns ou chats também é uma contribuição. |

## O que esperar de si mesmo

- Seu primeiro pull request provavelmente levará mais tempo do que você espera, principalmente por causa da configuração do ambiente e da leitura do projeto. Isso é normal.
- Alguns pull requests nunca são mesclados. Muitas vezes, os motivos não têm relação com a qualidade do seu código: o mantenedor está ocupado, a direção do projeto mudou ou outra pessoa resolveu o problema primeiro. O capítulo 8 aborda isso.
- Consistência vale mais do que quantidade. Cinco pull requests mesclados em um projeto ensinam mais e ficam melhor no seu histórico do que um pull request em cada um de cinquenta projetos.

## Lista de verificação

- [ ] Sei que tipo de contribuição quero fazer primeiro (código, documentação, testes ou triagem).
- [ ] Tenho um ou dois projetos em mente que realmente uso ou com os quais me importo.
- [ ] Estou planejando uma primeira contribuição pequena, não uma funcionalidade grande.
